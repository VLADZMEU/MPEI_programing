# 2. ОБЩИЕ СТАНДАРТЫ ОФОРМЛЕНИЯ

## 2.1. Размеры массивов

Стандартное ограничение для размера массива:

**n ∈ [1;10]**

Размер массива не должен превышать 10 элементов.

Это стандартное ограничение для всех массивов программы, если в условии конкретной задачи явно не указано иное.

Для двумерных массивов каждая размерность по умолчанию также находится в диапазоне [1;10]:

- количество строк: n ∈ [1;10];
- количество столбцов: m ∈ [1;10].

Если в программе несколько массивов, для каждого укажи его размерность и ограничения.

Обязательно отражай эти ограничения в УПЗ, таблице данных, входной форме, блок-схеме и тестах.

### Обработка неправильного размера

Если пользователь вводит n<1 или n>10:

1. Программа должна обнаружить аномалию.
2. Вывести сообщение об ошибке или просьбу повторить ввод.
3. Повторно запросить размер массива.
4. Продолжить выполнение только после получения допустимого значения.

Если исходный код не реализует такое поведение, обязательно укажи это как ошибку программы. Не изображай повторный ввод на блок-схеме, если его фактически нет в коде.

## 2.2. Стандартные форматы данных

Не путай формат вывода `printf` с форматом чтения `scanf`. При описании ввода указывай фактический формат преобразования из исходного кода.

Если в программе используется другой формат, укажи расхождение и проверь, нужно ли его исправить.

## 4.2. УПЗ

УПЗ всегда оформляй по одной структуре.

**Дано:**

Перечисление всех исходных данных, их типов, размеров и допустимых диапазонов.

Для массивов обязательно указывай стандартные ограничения:

n ∈ [1;10].

Для двумерных массивов указывай обе размерности.

**Нужно:**

Точное описание того, что требуется найти, вычислить, проверить или вывести.

**Условия выполнения и обработки аномалий:**

Здесь обязательно описывай поведение программы при возникновении аномалий.

Не ограничивайся простым перечислением ошибок.

Для каждой существенной аномалии укажи, что именно делает программа.

Примеры:

- Если n<1 или n>10, вывести сообщение о неправильном размере и повторно запросить n.
- Если искомый элемент отсутствует, вывести `Not found`.
- Если ни один элемент не удовлетворяет заданному условию, вывести соответствующее сообщение.
- Если входные данные имеют неправильный формат, сообщить об ошибке и запросить корректный ввод, если такая обработка реализована.
- Если невозможно выполнить математическую операцию, вывести соответствующее сообщение.

Поведение должно соответствовать реальному коду.

Если необходимая обработка отсутствует, отметь это как ошибку реализации.

**УПЗ должно описывать не только то, что программа получает и вычисляет, но и то, как она реагирует на неправильные данные и отсутствие результата.**

Соблюдай стиль и порядок из предоставленных образцов.

## 4.5. Входная форма

Ввод всегда стандартный — через stdin.

Не используй ввод из файлов, если этого прямо не требует задание.

Оформи входную форму по примеру документации.

Обязательно отрази:

- запрос количества элементов;
- ввод каждого исходного массива;
- ввод строк и столбцов, если массив двумерный;
- порядок ввода;
- типы данных;
- форматы ввода;
- проверки допустимого размера.

Для двумерного массива отдельно покажи, что сначала вводится размерность, а затем элементы массива.

Для нескольких массивов разделяй ввод каждого массива.

Входная форма должна соответствовать реальной последовательности `scanf` и других функций ввода.

Показывай текст приглашений к вводу так, как он реализован в программе.

Не ограничивайся записью `Ввод массива A`.

Используй понятную форму:

- «Введите количество элементов массива A:»
- «Введите элементы массива A:»
- «Введите количество строк:»
- «Введите количество столбцов:»
- «Введите элементы массива B:»

Это примеры формулировок, а не обязательные строки программы.

Если предусмотрен повторный ввод размера, отрази его в схеме входа.

## 4.6. Выходная форма

Вывод всегда стандартный — через stdout.

Оформи выходную форму по примеру документации.

Обязательно отрази:

- основной результат программы;
- все дополнительные результаты;
- результаты вычислений;
- результирующие массивы;
- сообщения об успешном выполнении;
- сообщения об отсутствии искомых элементов;
- сообщения об аномалиях;
- сообщения о повторном вводе.

Если программа выводит несколько массивов, укажи каждый отдельно.

Если результат представляет собой число, укажи его формат.

Если выводится `Not found`, `Еще раз`, `Повторите ввод` или другое сообщение, обязательно включи его.

Не ограничивайся только нормальным результатом.

Выходная форма должна полностью соответствовать реальному `printf` и другим функциям вывода в программе.

## 4.8. Блок-схемы

Блок-схемы являются одним из самых важных элементов документации.

Создавай их в diagrams.net (draw.io).

Предоставляй:

- редактируемый файл `.drawio`;
- экспорт в PNG;
- при возможности экспорт в SVG;
- отдельную блок-схему основной программы;
- отдельную блок-схему каждой подпрограммы.

Не заменяй полноценные блок-схемы текстовым описанием или Mermaid.

### Основная блок-схема

Блок-схема должна точно отражать алгоритм исходного кода.

Соблюдай следующие требования.

**1. Начало и конец**

Используй овальные блоки:

- «Начало»;
- «Конец».

**2. Ввод и вывод**

Используй параллелограммы.

Внутри указывай конкретные действия:

- ввод n;
- ввод элементов массива;
- вывод результата;
- вывод сообщения об ошибке.

**3. Обработка данных**

Используй прямоугольники.

В них указывай:

- присваивания;
- вычисления;
- изменение счётчиков;
- обновление результатов;
- операции с массивами.

**4. Условия**

Используй ромбы.

Все ветви должны быть подписаны:

- «Да» / «Нет»;
- либо `+` / `−`, как в примерах.

**5. Циклы**

Особенно важно правильное оформление циклов.

Если в коде используется `for`, оформляй цикл именно как `for`.

Если используется `while`, оформляй цикл именно как `while`.

Не заменяй один вид цикла другим.

Сохраняй:

- начальное значение счётчика;
- условие продолжения;
- изменение счётчика;
- тело цикла;
- точку выхода;
- направление обратной стрелки.

Ориентируйся на оформление циклов в примерах преподавателя.

Для вложенных циклов каждый цикл должен быть виден отдельно.

Если в коде два вложенных цикла, на схеме должна быть очевидна вложенность первого и второго цикла.

Не допускай, чтобы изменение счётчика оказалось вне тела или в неправильной части алгоритма.

Не объединяй несколько циклов в один условный блок.

**6. Обработка аномалий**

Каждая проверка размера массива должна присутствовать на блок-схеме.

Если n<1 или n>10:

- должна быть показана проверка;
- должна быть ветвь ошибки;
- должно быть сообщение о неправильном размере;
- должен быть показан повторный ввод, если он предусмотрен программой.

**7. Соединители**

Если блок-схема слишком большая:

- дели её на логические части;
- используй нумерованные соединители;
- обозначай одинаковыми номерами связанные переходы;
- не проводи стрелки через другие блоки;
- не создавай пересечения, затрудняющие чтение.

**8. Вызовы функций**

Каждый вызов подпрограммы показывай соответствующим блоком подпрограммы.

Не заменяй вызов функции обычным прямоугольником, если функция имеет собственную блок-схему.

**9. Проверка основной схемы**

Перед завершением проверь:

- соответствует ли количество циклов коду;
- соответствует ли количество условий;
- правильно ли расположены счётчики;
- все ли ветви отражены;
- все ли проверки аномалий показаны;
- нет ли пропущенных действий;
- нет ли лишних блоков;
- соответствует ли последовательность выполнения исходному коду.

### Блок-схемы подпрограмм

Каждая подпрограмма должна иметь ОТДЕЛЬНУЮ блок-схему и ОТДЕЛЬНУЮ таблицу данных.

Для каждой подпрограммы соблюдай порядок:

1. Сигнатура функции.
2. Таблица переменных этой функции.
3. Блок-схема этой функции.

Пример:

`int inputText(char *a, int n)`

Оформление блока подпрограммы должно соответствовать приложенному образцу:

- сверху указываются входные параметры `a, n`;
- в центральной части находится название функции `inputText`;
- в правой нижней части указываются выходные переменные или возвращаемое значение.

Не используй обычное обозначение «Начало» вместо обозначения входных параметров.

Не выдумывай выходные параметры.

Если функция возвращает значение, обязательно укажи его.

Если функция изменяет данные по указателю, отрази это в выходных переменных.

После обозначения подпрограммы подробно изобрази её внутренний алгоритм.

Не ограничивайся только вызовом функции.

Если в программе три подпрограммы, должно быть три отдельные таблицы и три отдельные блок-схемы, не считая основной.

**Каждая подпрограмма должна быть оформлена как самостоятельная алгоритмическая единица.**

## 4.9. Тесты

Тестирование должно быть максимально полным.

**Минимум 12 тестов.**

Если для полноценной проверки требуется больше, добавляй больше.

Запрещено составлять тесты, которые отличаются только несущественными числами и проверяют один и тот же сценарий.

Используй таблицу:

| № | Входные данные | Результат | Смысл теста |
|---|---|---|---|

Обязательно включай подходящие для задачи сценарии:

1. Контрольный пример с обычными данными.
2. Минимально допустимый размер n=1.
3. Максимально допустимый размер n=10.
4. Размер n=0.
5. Размер n=11.
6. Повторный ввод после неправильного размера.
7. Минимальные значения элементов.
8. Максимальные значения элементов, если ограничения существуют.
9. Отрицательные элементы.
10. Нулевые элементы.
11. Все одинаковые элементы.
12. Несколько элементов, удовлетворяющих условию.
13. Отсутствие элементов, удовлетворяющих условию.
14. Граничное значение условия.
15. Разные значения в соседних строках или столбцах, если применимо.
16. Все элементы массива, удовлетворяющие условию.
17. Ни одного подходящего элемента.
18. Другие специфические аномалии задачи.

Это перечень возможных сценариев, а не требование применять каждый из них к любой задаче.

Для двумерных массивов дополнительно проверяй:

- одинаковые элементы в разных строках;
- одинаковые элементы в разных столбцах;
- пустые по условию строки;
- строки или столбцы с полностью подходящими элементами;
- различные комбинации элементов;
- случаи, когда подходящих элементов нет.

Для задач с поиском проверяй:

- элемент в начале массива;
- элемент в конце массива;
- элемент в середине массива;
- несколько подходящих элементов;
- отсутствие искомого элемента.

Для задач с вычислениями проверяй:

- обычные значения;
- нули;
- отрицательные значения;
- граничные случаи;
- отсутствие данных для вычисления.

### Требования к результатам тестов

Каждый результат должен быть рассчитан вручную или проверен пошаговым выполнением алгоритма.

Не придумывай ожидаемые результаты.

Для каждого теста укажи:

- конкретные входные данные;
- полный ожидаемый результат;
- сообщение программы, если оно появляется;
- смысл проверки.

Для массивов указывай все элементы, а не только их размер.

Если программа после неправильного размера запрашивает повторный ввод, покажи всю последовательность:

1. Ввод неправильного значения.
2. Сообщение программы.
3. Повторный ввод.
4. Продолжение программы.
5. Итоговый результат.

После составления таблицы проверь, что:

- все условия программы протестированы;
- все ветви if/else пройдены хотя бы один раз;
- все циклы проверены;
- проверены граничные значения;
- все предусмотренные аномалии присутствуют;
- тесты не дублируют друг друга.

**Нельзя считать тест полноценным, если в нём отсутствует конкретный ожидаемый результат.**

# 5. ЕДИНСТВО ДОКУМЕНТАЦИИ

Все восемь разделов должны быть полностью согласованы между собой.

Особенно важно:

- УПЗ соответствует условию задачи.
- УПЗ описывает поведение при аномалиях.
- Размеры массивов соответствуют ограничению n ∈ [1;10].
- Таблица основной программы содержит все переменные.
- Каждая подпрограмма имеет собственную таблицу.
- Входная форма соответствует реальному вводу.
- Выходная форма соответствует реальному выводу.
- Аномалии отражены в выходной форме.
- Аномалии присутствуют в блок-схеме.
- Основная блок-схема соответствует исходному коду.
- Каждая подпрограмма имеет отдельную блок-схему.
- Таблица каждой подпрограммы соответствует её блок-схеме.
- Тесты проверяют все значимые участки алгоритма.

Нельзя допускать, чтобы:

- в таблице была переменная, отсутствующая в программе;
- в программе была переменная, отсутствующая во всех таблицах;
- блок-схема содержала действие, которого нет в алгоритме;
- отсутствовала блок-схема какой-либо функции;
- отсутствовала таблица какой-либо функции;
- тесты не проверяли аномалии;
- УПЗ не объясняло поведение при аномалиях;
- формат данных был указан неправильно.

# 6. ФИНАЛЬНАЯ ПРОВЕРКА

Перед выдачей результата проведи собственную проверку по следующим критериям:

1. Все восемь разделов присутствуют.
2. Структура УПЗ единообразна.
3. УПЗ содержит описание поведения при аномалиях.
4. Размер массива ограничен диапазоном [1;10], если задание не устанавливает иное.
5. Формат int — `%2d`.
6. Формат float — `%5.2f`.
7. Таблица основной программы содержит все переменные.
8. Каждая подпрограмма имеет отдельную таблицу.
9. Ввод стандартный.
10. Выходная форма содержит все сообщения.
11. Все возможные для задачи аномалии рассмотрены.
12. Основная блок-схема соответствует коду.
13. Каждый цикл оформлен правильно.
14. Вложенные циклы оформлены с правильной вложенностью.
15. Каждая подпрограмма имеет отдельную блок-схему.
16. На каждой схеме правильно обозначены входные и выходные переменные.
17. Не добавлено лишних блоков.
18. Есть не менее 12 различных тестов.
19. Тесты охватывают все значимые условия и аномалии.
20. Все ожидаемые результаты проверены.
21. Нет противоречий между разделами.

Если хотя бы один пункт не выполнен, исправь документацию до выдачи результата.

# 7. ФОРМАТ ОТВЕТА

Выдай результат в следующем порядке:

1. Краткий анализ исходного кода и соответствия заданию.
2. Полная документация из восьми разделов.
3. Таблица переменных основной программы.
4. Отдельная таблица и блок-схема для каждой подпрограммы.
5. Файлы блок-схем в формате draw.io и их изображения.
6. Таблица тестов (не менее 12).
7. Результаты финальной проверки.
8. Перечень обнаруженных ошибок исходного кода или документации.

Не сокращай таблицы ради компактности.

Не пропускай переменные.

Не ограничивайся приблизительными блок-схемами.

Не пиши «всё проверено», если фактически не проверил.

Если создание файлов draw.io недоступно, честно укажи это и предоставь редактируемый исходный XML, совместимый с diagrams.net, вместо выдуманной ссылки на файл.
